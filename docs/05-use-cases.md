# 5. Use cases

## UC-01 — Пользователь входит по email

**Основной актор:** пользователь  
**Предусловия:** приложение установлено; доступен email.

**Основной сценарий**
1. Пользователь открывает приложение.
2. Приложение предлагает авторизоваться по кнопке "авторизация".
3. Пользователь нажимает кнопку "авторизация".
4. Приложение переходит на экран ввода email.
5. Пользователь вводит email и отправляет форму.
6. Backend сохраняет email во временном хранилище, генерирует одноразовый код (TTL 10 минут), привязывает его к email и отправляет код на указанный адрес. Статус ответа всегда успешный (202 Accepted).
7. Приложение переходит на экран ввода кода подтверждения.
8. Пользователь открывает почтовый клиент, копирует код и вводит его в приложение.
9. Приложение отправляет введенный код в Backend для валидации.
10. Backend валидирует связку "email + code" по временному хранилищу. Если связка верна, ищет пользователя в основной базе по email. Если запись отсутствует, создает новую учетную запись. Если запись существует, находит пользователя.
11. Backend выдаёт сессию; приложение открывает основной экран.

**Альтернативные сценарии**
- A1: неверный код — клиент показывает ошибку.
- A2: подтверждение истекло — пользователь запрашивает новое.
- A3: сеть недоступна — отображается ошибка с возможностью повтора.
- A4: лимит попыток превышен — запрос временно ограничивается.

**Постусловие:** у приложения есть действующая пользовательская сессия.

## UC-02 — Пользователь подключается к VPN

**Основной актор:** пользователь  
**Предусловия:** пользователь вошёл; доступен хотя бы один сервер; устройство поддерживает VPN.

**Основной сценарий**
1. Пользователь открывает главный экран.
2. Приложение показывает текущее состояние (disconnected).
3. Пользователь выбирает сервер из списка (либо оставляет сервер, выбранный приложением автоматически, если такое правило будет принято. По умолчанию — ближайший по задержке или наименее загруженный).
4. Пользователь инициирует подключение.
5. Клиент запрашивает у backend актуальную Xray-конфигурацию для выбранного сервера
6. Native-компонент запрашивает системное разрешение, если оно необходимо.
7. Клиент получает/обновляет конфигурацию подключения через backend.
8. Native-компонент устанавливает Xray-туннель.
9. Клиент получает событие о состоянии туннеля.
10. UI показывает `connected`.

**Альтернативные сценарии**
- A1: пользователь отклоняет системное разрешение — подключение не начинается.
- A2: сервер недоступен — показывается ошибка, предлагается повтор или другой сервер.
- A3: конфигурация не получена — туннель не запускается.
- A4: туннель не поднялся — UI не показывает `connected`.
- A5: пользователь нажимает отключение во время подключения — система корректно отменяет/завершает попытку.
- А6: пользователь теряет интернет - срабатывает таймаут (например, 15 секунд), туннель должен быть отменен, UI покажет «Ошибка сети
- А7: конфликт с другим VPN - приложение показывает: "Отключите другой VPN-клиент и повторите попытку".
- А8: Ошибка Handshake - туннель запустился, но не может установить связь с сервером (неверный отпечаток, заблокирован провайдером). Native-компонент сообщает об ошибке Handshake failed. Приложение показывает: "Сервер недоступен или заблокирован. Попробуйте другой регион".

**Постусловие:** VPN подключён либо UI показывает, что подключение не удалось.
