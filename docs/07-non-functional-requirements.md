# 7. Non-functional requirements

**Статус:** Draft — численные SLO предстоит согласовать.

| ID | Область | Требование / цель | Как проверить |
|---|---|---|---|
| NFR-001 | Безопасность | Передача API-данных должна выполняться по защищённому каналу TLS (TLS 1.3 или выше). | Проверка конфигурации и тесты |
| NFR-002 | Секреты | Приватные ключи и секреты (включая конфигурации Xray, API-токены) не должны попадать в обычные backend-логи, клиентские логи уровня INFO/DEBUG или аналитику. | Code review и тест логирования |
| NFR-003 | Сессии | Токены сессии должны храниться в защищённом хранилище платформы, а не в обычном незашифрованном хранилище приложения. | Проверка реализации |
| NFR-004 | Авторизация | Backend должен проверять права доступа на каждом защищённом endpoint на основе ролей (RBAC). | Негативные API-тесты |
| NFR-005 | Приватность | Сбор диагностических данных должен быть минимальным, документированным и не включать содержимое пользовательского трафика. | Аудит телеметрии |
| NFR-006 | Надёжность | UI должен отображать статус подключения на основе атомарного статуса от backend. При неопределенности или ошибке инициализации туннеля UI обязан показывать состояние "Подключение..." или "Ошибка", но не "Активно". | Интеграционные тесты |
| NFR-007 | Производительность | Целевые значения времени загрузки списка серверов и установки туннеля нужно определить после прототипа и измерений. | Бенчмарки на целевых устройствах |
| NFR-008 | Совместимость | Список поддерживаемых версий iOS и Android должен быть утверждён до разработки MVP. | Матрица тестирования |
| NFR-009 | Наблюдаемость | Ошибки API и подключения должны иметь диагностические коды без утечки секретов. | Тесты логирования |
| NFR-010 | Доступность | Статус подключения и основные действия должны быть доступны screen reader и не передавать смысл только цветом. | Ручной аудит доступности |
